# 新式 API 登录流程（2026-10-16 晚，浏览器 HAR 逆向 + 线上实测）

来源：用户浏览器 F12 导出的 HAR（原始文件**不入库**，原因见文末「安全说明」）。
本文件是**结构脱敏件**：真实值一律归一化（客户端 IP→`10.0.0.100`、设备标识→`000000000000`、
账号→`202400000000` 形态），**密文与页面令牌一律剔除**。

## 一句话结论

真实登录**不是**老式 `c=ACSetting` 协议，而是 **`:801` 的新式 REST/JSONP API**，
参数为**单个 AES 加密的 `params`**。老式协议在该部署上**不做真实认证**，
其 `msga='userid error2'` **不表示密码错误**（教训见文末）。

## 请求序列（实测原样）

| # | 请求 | 响应（节选） | 作用 |
|---|---|---|---|
| 1 | `GET http://10.0.0.1/drcom/chkstatus?callback=dr1002&jsVersion=4.X&v=<n>&lang=zh` | `dr1002({"result":0,...,"v46ip":"10.0.0.100",...})` | 取本机在校园网的 IP |
| 2 | `GET http://10.0.0.1:801/eportal/portal/page/loadConfig?callback=dr1001&program_index=&wlan_vlan_id=0&wlan_user_ip=<base64(IP)>&...&jsVersion=4.X&v=<n>&lang=zh` | `dr1001({"code":1,"msg":"加载页面设置信息成功！","data":{...,"login_method":"1","en_md5":"0",...,"rcn":"<rcn>"}})` | 取页面令牌 `rcn` |
| 3 | `GET http://10.0.0.1:801/eportal/portal/login?callback=dr1005&params=<AES>&jsVersion=4.2.1&v=<n>&lang=zh` | `dr1005({"result":1,"msg":"Portal协议认证成功！"})` | 真正的登录 |

要点：

- 登录是 **GET + query 里的单个 `params`**（不是 POST 表单）；`params` 需 URL 编码。
- `chkstatus` 在**门户同源端口**（本机 `:80`），登录与 `loadConfig` 在 **`:801`**。
- `rcn` 是 `loadConfig` 下发的**一次性页面令牌**，登录必须带上；缺失/过期时服务器回
  「当前页面已超时，请重新刷新页面」。实测两次登录各自取了当时最新的 `rcn`。
- 浏览器在登录前后还会打 `duodian/get_active_conf`（实测回 `{"result":0,"msg":"非ip范围"}`）
  与 `duodian/queryPageSet`（实测回 `{"result":1,"msg":"发送成功"}`）。
  二者**都不是认证必需**：本客户端不发这两个请求，线上登录同样被服务器受理（见下节）。

## `params` 的加密与明文结构

- 算法：**AES-128-ECB + PKCS7 + Base64**；密钥为 16 字节 UTF-8 串 `5c1d5ad4dea0e8dd`。
- 密钥来源是门户自己的脚本（公开值，非本项目秘密）：
  - `a41.js`：`aes_en: function (str, key='5c1d5ad4dea0e8dd') {`
  - `a40.js`：`_util={aes_en:function(str){return CryptoJS.AES.encrypt(str,CryptoJS.enc.Utf8.parse('5c1d5ad4dea0e8dd'),{mode:CryptoJS.mode.ECB,padding:CryptoJS.pad.Pkcs7}).toString();},...}`
- 解密后是**单层 JSON**，字段与顺序在两次实测登录中完全一致：

| # | 字段 | 实测值形态 |
|---|---|---|
| 1 | `login_method` | `1` |
| 2 | `user_account` | `",0," + 账号 + 运营商后缀`（实测后缀 `@cmcc`） |
| 3 | `user_password` | 明文密码（11 字符） |
| 4 | `wlan_user_ip` | `chkstatus` 的 `v46ip` **原值**（**不**再 base64） |
| 5 | `wlan_user_ipv6` | `""` |
| 6 | `wlan_user_mac` | 12 位十六进制（门户取本机网卡 MAC） |
| 7 | `wlan_ac_ip` | `""` |
| 8 | `wlan_ac_name` | `""` |
| 9 | `jsVersion` | `"4.2.1"` |
| 10 | `login_t` | `"0"` |
| 11 | `js_status` | `"0"` |
| 12 | `is_page` | `"1"` |
| 13 | `is_page_new` | 随机数，见下 |
| 14 | `terminal_type` | `1` |
| 15 | `lang` | `"zh-cn"` |
| 16 | `rcn` | `loadConfig` 下发的令牌 |

- **兼容性证明（强证据）**：用上述密钥解密实测密文，再**原样重加密**，得到与实测
  **逐字节相同**的 base64（两笔登录各一次）。这排除了「密钥/模式/填充/字段顺序」任一偏差。
- `is_page_new` 无协议含义：门户脚本取 `Math.floor(Math.random()*10000+500)`；
  实测两次分别为 `558` 与 `9997`，服务器**均接受**。
- `wlan_user_mac` 的来源是门户脚本里的**本机网卡 MAC**（脚本取 `macList[i]['online_mac']`
  分支；另有全零/全一两个哨兵值表示「取 MAC 失败」），与 `chkstatus` 回报的 `ss1`
  （AC 侧看到的 MAC）**不是同一个值**。

## 线上实测（2026-10-16 晚，本机，与产品无关的独立实现）

用**独立实现**（Node.js 自带 AES，不复用产品代码）复刻上述三步，在**在线态**下复登：

| 变量 | 取值 | 响应 |
|---|---|---|
| A | `wlan_user_mac` = 本机网卡 MAC | `dr1005({"result":0,"msg":"终端IP已在线！","ret_code":2})` |
| B | `wlan_user_mac` = `000000000000` | `dr1005({"result":0,"msg":"终端IP已在线！","ret_code":2})` |

结论：

1. **该通道被真实服务器受理**——AES 密文、`rcn`、16 字段全部通过解析并进入业务判定
   （否则会得到「参数解析失败」/「页面已超时」）。
2. **`wlan_user_mac` 不影响判定**：真实网卡 MAC 与全零得到**完全一致**的响应，
   故本客户端固定发 `000000000000` 是安全的。
3. 「已在线」判定**先于凭据校验**，因此在线态下无法用登录接口反证密码对错——
   密码对错须在**注销态**验证。

## 成功/失败判定（实测样本）

| 响应 | 含义 | 客户端归类 |
|---|---|---|
| `{"result":1,"msg":"Portal协议认证成功！"}` | 认证成功 | **成功** |
| `{"result":0,"msg":"终端IP已在线！","ret_code":2}` | 该终端已在线（先于凭据校验） | **成功**（链路已通；**不可**归为凭据错误，否则调度器会停止重试）。判据须**同时**含「已在线」与「终端」——只有终端 IP 在线才证明本机链路通了，「该账号已在线」不算 |
| `{"result":0,"msg":"账号或密码错误",...}` | 凭据错误（模拟器夹具） | 失败 + `vendor_code=2`（停止重试）。启发式须**同时**命中「凭据词（账号/密码/用户名）」与「否定词（错误/不正确/不存在/无效）」，否则「获取用户信息失败，请稍后重试」这类普通故障会被误判成密码错误并永久停止重试 |
| `{"result":0,"msg":"当前页面已超时，请重新刷新页面",...}` | `rcn` 缺失/过期 | 结构性不可用 → 回退老式协议 |
| 老式回退通道的 `msga='userid error2'` | **本部署不代表密码错误**（与凭据对错无关） | 仅当新式接口**确实不存在**时才采信；若接口在场却因登录步骤故障而回退，一律降级为「无法判定」交重试裁决 |

## 安全说明（为何原始 HAR 不入库）

`params` 用的是**门户页面里公开的密钥**加密的，所以**任何真实密文等价于明文**
（含账号与密码）——把 HAR 或其中的 `params` 收进仓库＝把凭据收进仓库。
本目录只保留：结构、字段语义、公开密钥、判定样本；
**永不**收录真实 `params`、密码、页面令牌 `rcn`、真实 IP/MAC/账号。

## 教训（务必记住，避免重蹈）

老式通道 `POST http://10.0.0.1/eportal/?c=ACSetting&a=Login`（门户同源 80 端口）
在该部署上返回 `信息页` + `msga='userid error1/2'`，**但这不代表真实认证结果**：
同一套正确账号+正确密码（已用 HAR 密文逐字节比对确认与浏览器提交值一致）在该通道上
**恒得 error2**。公开错误码表把 error2 解释为「密码不匹配」，直接把诊断误导了数小时。

**判定原则**：凡能与真实浏览器/官方客户端对照的，就以对照结果为准；
厂商错误码表仅作参考，且必须用「能成功的通道」复现过才可采信。
